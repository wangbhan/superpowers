# 系统化调试

## 概述

随意修复不仅浪费时间，还会引发新的错误。仓促的补丁只会掩盖根本问题。

**核心原则：**在尝试修复之前，务必先找出根本原因。仅修复症状是行不通的。

**违反此流程的字面规定，就是违背了调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

若未完成第一阶段，则不得提出修复方案。

## 适用场景

适用于任何技术问题：
- 测试失败
- 生产环境中的缺陷
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别适用于以下情况：**
- 时间紧迫时（紧急情况容易让人想靠猜测解决）
- “只需一个快速修复”看似显而易见
- 你已经尝试过多种修复方案
- 之前的修复方案未奏效
- 你尚未完全理解该问题

**以下情况请勿跳过：**
- 问题看似简单（简单的错误也有其根本原因）
- 你很着急（仓促行事必然导致返工）
- 经理要求“现在”就修复 （系统化排查比盲目摸索更快）

## 四个阶段

你必须完成每个阶段后才能进入下一阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告信息
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径和错误代码

2. **稳定重现问题**
   - 你能可靠地触发该问题吗？
   - 具体操作步骤是什么？
   - 是否每次都会发生？
   - 若无法复现 → 收集更多数据，切勿凭空猜测

3. **检查近期变更**
   - 哪些变更可能导致此问题？
   - 使用 Git diff 检查近期提交
   - 新增依赖项、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，请添加诊断代码：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪个层级出现故障（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误深埋在调用栈中时：**

   完整的逆向追踪技术请参见本目录中的 `root-cause-tracing.md`。

   **简要版本：**
   - 错误值源自何处？
   - 哪个调用者传入了错误值？
   - 向上追溯直至找到源头
   - 修复源头，而非症状

### 第二阶段：模式分析

**修复前先找出模式：**

1. **寻找正常运行的示例**
   - 在同一代码库中查找类似的正常运行代码
   - 哪些与故障代码相似的代码能够正常运行？

2. **与参考实现对比**
   - 若在实现某种模式，请完整阅读参考实现
   - 不要走马观花——逐行阅读
   - 应用前需完全理解该模式

3. **识别差异**
   - 正常运行的代码与出错的代码有何不同？
   - 列出所有差异，无论多么细微
   - 不要认为“这不重要”

4. **理解依赖关系**
   - 这需要哪些其他组件？
   - 需要哪些设置、配置和环境？
   - 它基于哪些假设？

### 第三阶段：假设与测试

**科学方法：**

1. **提出单一假设**
   - 明确表述：“我认为 X 是根本原因，因为 Y”
   - 将其写下来
   - 具体明确，避免模糊

2. **最小化测试**
   - 进行尽可能微小的更改来验证假设
   - 每次只调整一个变量
   - 不要同时修改多项内容

3. **验证后再继续**
   - 有效吗？是 → 进入第4阶段
   - 无效吗？提出新假设
   - 切勿在此基础上叠加更多修正

4. **遇到不明白的情况时**
   - 说“我不明白 X”
   - 不要装作明白
   - 寻求帮助
   - 进行更多研究

### 第 4 阶段：实施

**解决根本原因，而非症状：**

1. **创建失败的测试用例**
   - 尽可能简单的重现步骤
   - 如有可能，采用自动化测试
   - 若无框架，则编写一次性测试脚本
   - 修复前必须具备此用例
   - 使用 `superpowers:test-driven-development` 技巧编写正确的失败测试

2. **实施单一修复**
   - 解决已查明的根本原因
   - 每次只进行一项更改
   - 不要进行“既然已经在这里了”式的改进
   - 不要捆绑重构

3. **验证修复结果**
   - 测试现在通过了吗？
   - 是否有其他测试失败？
   - 问题是否真正得到解决？

4. **如果修复无效**
   - 停止
   - 统计：你尝试了多少次修复？
   - 如果 < 3：返回第 1 阶段，结合新信息重新分析
   - **若 ≥ 3：停止并质疑架构（见下文第 5 步）**
   - 未经架构讨论，切勿尝试修复方案 #4

5. **若 3 个及以上修复方案失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都会在不同位置暴露新的共享状态/耦合/问题
   - 实施修复需要“大规模重构”
   - 每次修复都会在其他地方引发新的症状

   **暂停并质疑根本问题：**
   - 这种模式在根本上是否合理？
   - 我们是否只是“出于惯性而坚持下去”？
   - 我们应该重构架构，还是继续修复症状？

   **在尝试更多修复方案之前，请先与你的同事讨论**

   这并非假设失败——而是架构本身有问题。

## 危险信号——停下来并遵循流程

如果你发现自己有以下想法：
- “先快速修复，以后再调查”
- “试着改改 X，看看能不能行”
- “添加多项修改，运行测试”
- “跳过测试，我手动验证一下”
- “大概是X的问题，我来修复它”
- “虽然没完全搞懂，但这可能行得通”
- “设计模式说的是X，但我会另作调整”
- “主要问题如下：[未经过调查就列出修复方案]”
- 在追踪数据流之前就提出解决方案
- **“再试一次修复”（当已经尝试过 2 次以上时）**
- **每次修复都会在不同位置暴露新问题**

**以上所有情况都意味着：停止。返回第 1 阶段。**

**如果 3 次及以上修复失败：** 质疑架构（参见第 4.5 阶段）

## 你的合作伙伴发出的“你做错了”信号

**注意以下这些话题转移：**
- “那不是没发生吗？”——你未经核实就做了假设
- “这会显示……吗？”——你本应补充收集证据的步骤
- “别再猜了”——你在未弄清情况时就提出修复方案
- “深入思考一下”——要质疑根本原因，而非仅关注症状
- “我们卡住了？”（沮丧）——你的方法行不通

**当你看到这些情况时：** 停止。返回第 1 阶段。

## 常见的自我辩解

| 借口 | 现实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单的问题也有根本原因。对于简单 bug，流程反而能加快解决速度。 |
| “紧急情况，没时间走流程” | 系统化的调试比盲目试错更快。 |
| “先试这个，再调查” | 首次修复会确立模式。从一开始就做对。 |
| “确认修复有效后再写测试用例” | 未经测试的修复无法持久。先测试才能验证。 |
| “一次修复多个问题能节省时间” | 无法确定是哪项修复起效。会导致新 bug。 |
| “参考资料太长，我改编一下模式” | 部分理解必然导致 bug。 请通读全文。 |
| “我看到问题了，让我来修复” | 看到症状 ≠ 理解根本原因。 |
| “再试一次修复”（在失败 2 次以上后） | 失败 3 次以上 = 架构问题。质疑模式，不要再修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根本原因** | 阅读错误信息、复现问题、检查变更、收集证据 | 理解“是什么”和“为什么” |
| **2. 模式** | 寻找可运行的示例、进行比较 | 识别差异 |
| **3. 假设** | 提出理论、进行最小化测试 | 假设得到证实或产生新假设 |
| **4. 实施** | 创建测试、修复、验证 | 缺陷已解决，测试通过 |

## 当流程显示“无根本原因”时

如果系统性调查表明问题确实是环境因素、时间依赖性或外部因素造成的：

1. 您已完成该流程
2. 记录您调查的内容
3. 实施适当的处理措施（重试、超时、错误信息）
4. 添加监控/日志以供未来调查

**但：** 95% 的“无根本原因”案例其实是调查不彻底所致。

## 辅助技术

这些技术是系统化调试的一部分，可在以下目录中找到：

## 实际影响

来自调试实践：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时的盲目摸索
- 首次修复率：95% 对比 40%
- 引入新缺陷：接近零 对比 常见
